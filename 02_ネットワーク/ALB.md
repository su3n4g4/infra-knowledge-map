# ALB（Application Load Balancer）

AWS が提供する L7 のロードバランサー。HTTPS を受けて TLS を解き、ターゲットグループに登録されたサーバーやコンテナのうち、ヘルスチェックに通ったものへ HTTP で転送する。

仕組みと設計の考え方は [[ロードバランサー]] にまとめています。この解説では、**ALB に固有の部品・初期値・動き** だけを扱います。

## なぜ必要か

ロードバランサーを自分で用意すると、ロードバランサー自体のサーバーの運用（台数、更新、そのサーバーが止まったときの切り替え）も自分で持つことになります。ALB を使うと、それを AWS に任せられます。

- ALB 自体が複数の AZ に置かれ、止まりにくい
- アクセスの増減に合わせて、ALB の処理能力を AWS が調整する
- ECS と組み合わせると、転送先の登録・解除が自動になる
- 証明書を ACM で発行し、更新も自動にできる

HTTP 以外の通信を扱う、IP アドレスを固定したいといった場合は、L4 の NLB を使います。

## 概念との対応

| ロードバランサーの概念 | ALB での名前 |
|---|---|
| 受け口 | リスナー（例：443 番） |
| 振り分けの条件 | リスナールール（パス、ホスト名など） |
| 転送先のリスト | ターゲットグループ |
| 転送先 | ターゲット（EC2 のインスタンス、ECS のタスクの IP:ポート） |
| 正常かどうかの確かめ方 | ターゲットグループのヘルスチェック設定 |
| 外すときに処理中を待つこと | 登録解除の遅延 |
| 後ろのサーバーに誰が届くか | セキュリティグループ |
| TLS の証明書 | ACM の証明書をリスナーに付ける |

```txt
[利用者]
   │ HTTPS :443
   ▼
┌──────────── ALB ────────────┐
│ リスナー :443（ACM の証明書）     │
│   ルール1：/api/*  → TG-api     │
│   ルール2：それ以外 → TG-web     │
└──────────────┬──────────────┘
               ▼
   ターゲットグループ TG-web
     ├ 10.0.2.11:8080  healthy
     ├ 10.0.2.12:8080  healthy
     └ 10.0.2.13:8080  unhealthy
```

## 初期値と変える値

| 設定 | 初期値 | 何に効くか | 変える目安 |
|---|---|---|---|
| アイドルタイムアウト | 60 秒 | アプリが応答しないまま、これを超えると 504 | 60 秒を超える処理があるなら延ばす。ただし先に、その処理を非同期にできないか考える |
| ヘルスチェックの間隔 | 30 秒 | 異常に気づくまでの速さ | 早く外したいなら短く |
| ヘルスチェックのタイムアウト | 5 秒 | この時間で応答が無ければ失敗 | ヘルスチェックの口が遅いなら見直す（口を軽くするのが先） |
| unhealthy のしきい値 | 2 回 | 何回続けて失敗したら外すか | 一時的な遅れで外れすぎるなら増やす |
| healthy のしきい値 | 5 回 | unhealthy になったターゲットが、何回続けて成功したら戻すか（新しく登録したターゲットは、1回成功すれば healthy になる） | 初期値だと戻るまで最大2分半かかる。一時的な不調から早く戻したいなら 2〜3 回に減らす |
| 登録解除の遅延 | 300 秒 | 外すときに処理中を待つ時間 | 処理が数秒で終わるアプリなら 30〜60 秒程度に縮めると、デプロイが速くなる |
| アクセスログ | 無効 | どのターゲットに転送し、どちらがエラーを返したかの記録 | 本番では有効にする（S3 に保存される） |

アプリ側の keep-alive は、アイドルタイムアウト（60 秒）より長くします。Nginx の `keepalive_timeout` は初期値が 75 秒なのでそのままでよく、Go は `http.Server` の `IdleTimeout` を設定します。

## 実装に固有の動き

### IP アドレスが変わる
ALB は、作成時に指定した複数の AZ のパブリックサブネットに実体を置き、AWS の都合で入れ替わります。そのため **IP アドレスは固定ではありません**。DNS では IP ではなく ALB の名前（Route 53 のエイリアスレコード）で指します → [[DNS]]

### ECS がターゲットを自動で登録・解除する
ECS のサービスにターゲットグループを指定しておくと、タスクが起動するたびに ECS がその IP:ポートを登録し、止めるときには登録を解除します → [[ECS]]

### 全部 unhealthy になると、全部に転送する（fail open）
ターゲットが全部 unhealthy になると、ALB は「どれも同じなら全部に転送する」動きをします。そのため、全滅していても 503 ではなく 502 や 504 として現れることがあります。

### 元の情報はヘッダで届く
ALB で TLS を解くと、アプリには HTTP で届き、送信元の IP も ALB のものになります。元の情報は次のヘッダで渡されます。

| ヘッダ | 中身 |
|---|---|
| `X-Forwarded-For` | 利用者の IP アドレス |
| `X-Forwarded-Proto` | 元のプロトコル（https） |

Laravel ではプロキシを信頼する設定（TrustProxies）をしないと、生成される URL が http になったり、利用者の IP を取れなかったりします。

### セキュリティグループで「ALB から」を指定できる
アプリのセキュリティグループで、許可する相手を IP ではなく **ALB のセキュリティグループ** で指定できます。ALB の IP が変わっても、設定を直す必要がありません。

## 障害

502・503・504 の基本的な意味は [[ロードバランサー]] を参照してください。ここでは ALB に固有のものだけを挙げます。

| 症状 | 原因 | 確かめ方 |
|---|---|---|
| 全ターゲットが unhealthy なのに 503 にならない | fail open で全部に転送している | 「unhealthy なら 503 のはず」と思い込まない。ターゲットグループの状態を直接見る |
| 503 | ターゲットグループにターゲットが1つも登録されていない | ECS のタスクが全部止まっていないか、ターゲットグループの登録状況を見る |
| アプリは正常なのに unhealthy | ヘルスチェックのパスやポートの不一致、セキュリティグループで ALB からの通信を許可していない | ターゲットグループの「ヘルスチェックの詳細」に失敗の理由が出る |
| ALB 宛ての接続が時々失敗する | ALB の IP を固定で設定していた | 設定ファイルや取引先の許可リストに、ALB の IP を書いていないか確かめる |
| どちらがエラーを返したか分からない | — | メトリクスの `HTTPCode_ELB_5XX_Count`（ALB が返した）と `HTTPCode_Target_5XX_Count`（アプリが返した）を見比べる |

取引先に「この IP からのアクセスを許可してほしい」と頼まれる場面では、ALB だけでは IP を固定できません。NLB や Global Accelerator を検討します。
