# ロードバランサー

1つの受け口（IP アドレスとポート）でリクエストを受け、後ろにある複数のサーバー（IP:ポート）のうち、正常に応答しているものを選んで転送する仕組み。オンプレでは Nginx や HAProxy、専用の機器で、AWS では ALB で実現する。

## なぜ必要か

アプリのサーバーが1台だけだと、2つの問題があります。

- **処理しきれない**：アクセスが増えると、1台の CPU やメモリでは追いつかなくなる
- **1台が止まると全部止まる**：障害でも、デプロイでの再起動でも、サービスが止まる

サーバーを2台以上に増やせば解決しそうですが、そうすると「利用者はどのサーバーに接続すればいいのか」という問題が出ます。DNS に IP アドレスを2つ登録する方法もありますが、片方が止まっても DNS はそれを知らないので、止まった方へ送り続けてしまいます。

そこで、**手前に受け口を1つだけ置き、後ろの複数台に転送する** のがロードバランサーです。後ろのサーバーが応答しているかを定期的に確かめているので、止まったサーバーには転送しません。

これで次のことができるようになります。

- 1台止まってもサービスは続く
- 台数を増やせば、処理できる量も増える
- 1台ずつ入れ替えれば、止めずにデプロイできる → [[ローリング更新]]

## 仕組み

### 基本の形

```txt
[利用者]
   │ 受け口：203.0.113.10:443
   ▼
[ロードバランサー]
   │ 転送先のリスト
   ├ 10.0.2.11:8080  正常   ← 転送する
   ├ 10.0.2.12:8080  正常   ← 転送する
   └ 10.0.2.13:8080  異常   ← 転送しない
```

ロードバランサーが持っている情報は、おおむね次の3つです。

| 情報 | 内容 |
|---|---|
| 受け口 | どの IP アドレス・ポートで待ち受けるか |
| 転送先のリスト | 後ろのサーバーの IP:ポートの一覧 |
| 正常かどうかの確かめ方 | どのパスに、どの間隔で問い合わせるか → [[ヘルスチェック]] |

### L4 と L7

ロードバランサーは、通信のどこまで中身を読むかで2種類に分かれます（OSI 参照モデルの層）。

| 種類 | 見るもの | できること |
|---|---|---|
| L4 | IP アドレスとポート | 接続ごとに転送先を決める。HTTP の中身は見ない |
| L7 | HTTP の中身（パス、ホスト名、ヘッダ） | `/api/*` は API サーバー、`admin.example.com` は管理画面、のように振り分ける |

### 接続はいったん終わる（終端）

L7 のロードバランサーは、利用者からの接続を **自分のところで終わらせ**、後ろのサーバーへは **新しい接続を張り直します**。

```txt
利用者 ══接続①（HTTPS）══▶ ロードバランサー ──接続②（HTTP）──▶ アプリ
                              ↑
                        ここで TLS も解ける
```

接続①と接続②は別物です。502・504 は、**接続②でロードバランサーが失敗した** ことを表します。

## 設計で決めること

### 1. L4 にするか L7 にするか
- 選択肢：L4（IP とポートだけを見る）／L7（HTTP の中身を見る）
- 判断の基準：パスやホスト名で振り分けたい、TLS をロードバランサーで解きたいなら L7。HTTP 以外の通信を扱う、送信元の IP をそのまま後ろに届けたい、とにかく速さを優先するなら L4

### 2. どこで TLS を解くか
- 選択肢：ロードバランサー／後ろのサーバー／両方（ロードバランサーで解いて、後ろへ暗号化し直す）
- 判断の基準：多くの場合はロードバランサー。証明書の管理が1か所で済み、アプリは HTTP だけを扱えばよい。内部の通信も暗号化する決まりがあるなら、後ろまで暗号化する → [[TLS]]

### 3. 転送先をどう選ぶか
- 選択肢：ラウンドロビン（順番に）／最小接続（処理中の接続がいちばん少ないところへ）
- 判断の基準：1件ごとの処理時間がそろっているならラウンドロビン。重いリクエストと軽いリクエストが混ざるなら最小接続

### 4. タイムアウトをどういう関係にするか
- 選択肢：ロードバランサーが接続②の無通信をどれだけ待つか（タイムアウト）と、アプリ側の時間の関係
- 判断の基準：次の2つを守る
  - アプリの処理時間 < ロードバランサーのタイムアウト（超えると 504）
  - アプリの keep-alive の時間 > ロードバランサーのタイムアウト（逆だと、アプリが先に閉じた接続をロードバランサーが使って 502）

### 5. セッションをどこに置くか
- 選択肢：Redis や DB などの共有の場所／同じ利用者を同じサーバーに送り続ける（スティッキーセッション）
- 判断の基準：基本は共有の場所。どのサーバーに届いても同じセッションを読める。スティッキーセッションは、古いアプリをすぐには直せないときの応急策。そのサーバーが止まるとセッションが消え、負荷も偏る

### 6. 外すときにどれだけ待つか
- 選択肢：転送先から外すとき、処理中のリクエストが終わるまで待つ時間（コネクションドレイニング）
- 判断の基準：一番長いリクエストの処理時間より少し長く。長すぎるとデプロイが遅くなる。アプリ側も、止める合図を受けたら処理中を終えてから終了する → [[グレースフルシャットダウン]]

### 7. 後ろのサーバーに誰が届けるか
- 選択肢：ロードバランサーからだけ届く／ほかからも届く
- 判断の基準：ロードバランサーからだけにする。ファイアウォールで絞らないと、ロードバランサーでの TLS や制限を素通りして、アプリを直接叩かれる

## 障害

主語は **ロードバランサー**、相手は **後ろのサーバー（接続②）** です。

| 症状 | 原因 | 確かめ方 |
|---|---|---|
| 502 Bad Gateway | 後ろのサーバーから正しい応答が返らなかった、または接続を切られた。アプリのプロセスが落ちた、アプリの keep-alive がロードバランサーより短い、デプロイ時に処理中の接続を切った | ブラウザや DB ではなく、ロードバランサーと後ろのサーバーの間を見る。ロードバランサーのログで、どのサーバーへの転送で失敗したかを調べる |
| 503 Service Unavailable | 転送できるサーバーが無い。全台が止まっている、転送先の設定ミス | 転送先のリストと、各サーバーの状態を見る |
| 504 Gateway Timeout | 後ろのサーバーが時間内に応答しない。重い処理、DB の待ち（[[N+1問題]]）、外部 API の待ち | アプリのログで、そのリクエストの処理時間を見る |
| 時々 502 が出る | アプリが落ちては起動し直している | プロセスの起動時刻が新しすぎないかを見る。ネットワークの不調と誤解しやすい |
| アプリは正常なのに、全台が異常と判断される | ヘルスチェックのパスやポートがアプリと合っていない、ファイアウォールで問い合わせが届いていない | 新しく構成を作ったときに最も起きやすい。ロードバランサーから問い合わせているパスを、自分でも叩いてみる |
| 時々ログアウトされる | セッションをサーバーのメモリやファイルに持っていて、別のサーバーに転送された | セッションの保存先の設定を見る。1台のときは起きなかったなら、ほぼこれ |

## 実行モデルで変わること
→ [[実行モデル]]

| | 作り直す型（PHP-FPM） | 常駐型（Go など） |
|---|---|---|
| ロードバランサーの後ろ | Nginx → PHP-FPM | アプリに直結できる |
| keep-alive を設定する場所 | Nginx の `keepalive_timeout` | アプリのサーバー設定（Go なら `IdleTimeout`） |
| プロセスが落ちたとき | 残りの worker が応答を続ける | 全部のリクエストが失敗し、502 が出やすい |

## 実装の例

| 環境 | 実装 |
|---|---|
| オンプレ | Nginx（`upstream`）、HAProxy、専用の機器 |
| AWS | [[ALB]]（L7）、NLB（L4） |

Nginx でロードバランサーにする場合の設定例：

```nginx
upstream app {
    least_conn;                  # 最小接続で選ぶ
    server 10.0.2.11:8080;
    server 10.0.2.12:8080;
    keepalive 32;                # 後ろのサーバーとの接続を使い回す
}

server {
    listen 443 ssl;
    location / {
        proxy_pass http://app;   # upstream に転送する
    }
}
```

標準の Nginx は、転送してエラーになったサーバーをしばらく外しますが、決まった間隔で問い合わせるヘルスチェックはありません。必要なら HAProxy や専用の機器を使います。
