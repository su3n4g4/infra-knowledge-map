# TLS

TCP の接続の上で、送受信するデータを暗号化し、接続先のサーバーが本物かを証明書で確かめるプロトコル。HTTP を TLS の上で送るのが HTTPS。

## なぜ必要か

インターネットの通信は、利用者からサーバーまでの間に多くの機器を経由します。暗号化しないと、途中の機器でパスワードやカード番号を読まれたり、ページの中身を書き換えられたりするおそれがあります。

もう1つの役割は、**相手が本物か確かめること** です。暗号化していても、相手が偽物のサーバーなら意味がありません。TLS では、サーバーが「信頼できる機関が発行した証明書」を見せることで、本物であることを示します。

## 仕組み

### ハンドシェイク

TCP で接続したあと、本番の通信の前に、暗号の鍵を決めるやりとりをします。

```txt
ブラウザ                          サーバー
  │── TCP 接続（3-way handshake）──│
  │── ClientHello ────────────────▶│ 使える暗号の種類を伝える
  │◀─ 証明書・鍵の材料 ──────────────│ 本物の証明と、鍵の交換
  │   （証明書が本物か確かめる）      │
  │══════ 以降は暗号化された通信 ═════│
```

- **証明書**：「このドメインのサーバーはこの公開鍵を持っている」と、認証局が保証したもの。期限がある
- ハンドシェイクは往復が多いので、**遠い利用者ほど待ち時間が長くなる**

### TLS 終端

暗号を解く場所を **TLS 終端** と呼びます。終端より内側は、暗号化されていない通信（平文）になります。

```txt
[利用者] ══暗号化══▶ [ロードバランサーで終端] ──平文──▶ [アプリ]
                                         └ 内部のネットワークなので、平文でも許容されることが多い
```

終端したあと、アプリには HTTP で届きます。元が HTTPS だったかは、ロードバランサーが付ける `X-Forwarded-Proto` ヘッダで分かります。

## 設計で決めること

### 1. どこで TLS を終端するか
- 選択肢：ロードバランサー／Web サーバー（Nginx など）／アプリまで暗号のまま
- 判断の基準：多くの場合はロードバランサー。証明書を1か所で管理でき、アプリは HTTP だけを扱えばよい。法令や社内規定で内部の通信も暗号化が必要なら、アプリまで暗号のままにする

### 2. 証明書をどう更新するか
- 選択肢：手動で更新する／自動で更新する仕組みを使う
- 判断の基準：自動で更新する。期限切れは、監視していないと必ず起きる事故になる。手動で入れた証明書は、期限を監視してアラートを出す

### 3. アプリに元のプロトコルを伝えるか
- 選択肢：`X-Forwarded-Proto` などのヘッダを信頼する設定をする／しない
- 判断の基準：終端したなら設定する。しないと、アプリが「HTTP で来た」と判断し、生成する URL が http になったり、HTTPS への転送を繰り返したりする。Laravel では TrustProxies の設定がこれにあたる

## 障害

| 症状 | 原因 | 確かめ方 |
|---|---|---|
| ブラウザが「この接続ではプライバシーが保護されません」と出す | 証明書の期限切れ、ドメイン名と証明書が合っていない | ブラウザで証明書の期限と対象のドメイン名を見る |
| 遠い地域の利用者だけ、最初の表示が遅い | ハンドシェイクの往復に時間がかかっている | 利用者に近い場所で終端できないか検討する → [[CDN]] |
| リダイレクトがループする | ロードバランサーで終端したのに、アプリが「HTTP で来た」と判断して HTTPS へ転送し続ける | アプリが `X-Forwarded-Proto` を信頼する設定になっているか見る |

## 実装の例

| 環境 | 実装 |
|---|---|
| オンプレ | Let's Encrypt などで発行した証明書を、Nginx やロードバランサーの機器に置く |
| AWS | ACM で発行した証明書を、ALB や CloudFront に付ける（更新は自動） |
