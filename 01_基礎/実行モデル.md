# 実行モデル（作り直す型と常駐型）

Web アプリのプロセスが、1リクエストごとに状態を捨てる「作り直す型」か、1つのプロセスがずっと動いて多数のリクエストを同時に処理する「常駐型」か、という動き方の違い。

## なぜ必要か

同じロードバランサーや DB を使っていても、アプリの動き方によって、気をつける場所がまったく変わります。

- タイムアウトや同時処理数を、どこで設定するのか
- DB の接続数を、どう数えるのか
- 1つのバグが、どこまで被害を広げるのか

これらは言語の文法ではなく、**プロセスがどう動くか** で決まります。言語ではなく動き方で分けて覚えておくと、新しい言語やフレームワークに出会っても、どちらの型かを見分けるだけで注意点が分かります。

## 仕組み

### 作り直す型

```txt
Nginx ──▶ PHP-FPM
            ├ worker 1：リクエスト A を処理 → 終わったら状態を全部捨てる
            ├ worker 2：リクエスト B を処理 → 終わったら状態を全部捨てる
            └ worker 3：空き
```

- 1つの worker が、一度に1つのリクエストだけを処理する
- リクエストが終わると、変数も DB の接続も捨てる（シェアードナッシング）
- 代表例：PHP-FPM

### 常駐型

```txt
1つのプロセス（ずっと動いている）
  ├ リクエスト A ┐
  ├ リクエスト B ├ 同時に処理
  ├ リクエスト C ┘
  └ DB の接続プール、キャッシュなど ← リクエストをまたいで持ち続ける
```

- 1つのプロセスが、たくさんのリクエストを同時に処理する
- プロセスが生きている間、メモリ上の状態を持ち続ける
- 代表例：Go、Node.js、Java（Spring など）

### いちばん大事な見方：責任の移動

作り直す型では、Nginx や PHP-FPM が引き受けていた責任があります。タイムアウト、同時処理数の上限、止め方などです。常駐型では、これらの多くが **アプリのコードの責任** に移ります。

```txt
作り直す型：アプリ ＋ Nginx・PHP-FPM の設定 ＝ 守り
常駐型    ：アプリのコード             ＝ 守り（自分で書かないと、無い）
```

各解説の「実行モデルで変わること」には、この **責任がどちらにあるか** の違いを書いています。

## 比較

| 観点 | 作り直す型 | 常駐型 |
|---|---|---|
| 同時処理の単位 | worker プロセス | goroutine、イベントループ、スレッドなど |
| 同時処理の上限 | worker 数で自然に決まる | 自分で決める |
| 状態の持ち越し | しない（毎回まっさら） | する（接続プールが使える。メモリリークも起きうる） |
| DB の接続 | リクエストごとに張って捨てる | プールで使い回す |
| 1件の致命的なエラー | その worker だけが落ちる | プロセス全体が落ちることがある |
| タイムアウトや上限の設定 | Nginx や PHP-FPM の設定ファイル | アプリのコード |

常駐型の中にも違いがあります。

| 観点 | Go | Node.js |
|---|---|---|
| 同時に処理する仕組み | goroutine を複数の OS スレッドで同時に動かす | 1本のスレッドで、待ち時間に別の処理へ切り替える（イベントループ） |
| 重い計算をすると | 他の goroutine は別のスレッドで動ける | その間、ほかのリクエストが全部止まる |

どちらも常駐型なので、接続プールやメモリリーク、エラー時の影響範囲の考え方は同じです。

## 当てはめ方

### 1. 使っている言語やフレームワークが、どちらの型か見分ける
- 見分け方：「1つのプロセスが、リクエストの間もずっと生きていて、変数を持ち続けるか」を確かめる。持ち続けるなら常駐型
- 気をつけること：PHP でも、Swoole や RoadRunner、Laravel Octane を使うと常駐型になる。同じ言語でも動かし方で型が変わる

### 2. 作り直す型から常駐型へ移るとき
- 見分け方：Nginx や PHP-FPM の設定で決めていたことを、洗い出す
- 気をつけること：タイムアウト（→ [[Goのnet_http]]）、同時処理数の上限、DB の接続の上限（→ [[接続プール]]）、止め方（→ [[グレースフルシャットダウン]]）、panic などの致命的なエラーの受け止め方（→ [[panicとrecover]]）を、コードで持つ必要がある

### 3. 障害を調べるとき
- 見分け方：「1つのリクエストの失敗が、ほかのリクエストに波及しているか」を見る
- 気をつけること：常駐型で「時々、全部のリクエストが失敗する」なら、プロセスが落ちて起動し直している可能性が高い。「じわじわメモリが増える」なら、リクエストをまたいで何かが溜まっている
