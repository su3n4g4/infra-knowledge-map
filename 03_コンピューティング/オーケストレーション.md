# オーケストレーション

「このプログラムを、この CPU・メモリで、N 個動かす」という指定と、実際に動いているプロセスやコンテナを比べ続け、足りなければ起動し、止まったものは起動し直して、指定どおりの状態を保つ仕組み。1台の中では systemd、複数台をまとめるなら Kubernetes、AWS では ECS で実現する。

## なぜ必要か

アプリを動かし続けるには、起動したあとも次の作業が続きます。

- プロセスが落ちたら、起動し直す
- サーバーが丸ごと止まったら、別のサーバーで起動し直す
- アクセスが増えたら数を増やし、減ったら減らす
- 新しい版に、1つずつ入れ替える

台数が少ないうちは、SSH でサーバーに入り、コマンドで手作業できます。でも数が増えると、人の手では回りません。夜中に落ちたプロセスに、朝まで誰も気づかないこともあります。

オーケストレーションは、これを **「指定された状態」と「実際の状態」を比べて、ずれを直す** という1つのルールで自動にします。

## 仕組み

### ずれを直し続ける

```txt
指定：「アプリを 4 個」
   ↓ 比べる
実際：3 個（1個が落ちた）
   ↓ ずれ：1個足りない
動作：1個を起動する
   ↓ また比べる（これをずっと繰り返す）
```

人が渡すのは「どうなっていてほしいか」だけです。「どう直すか」の手順は書きません。

### 管理する範囲

| 範囲 | 管理するもの | できること | 例 |
|---|---|---|---|
| 1台の中 | プロセス | 落ちたら起動し直す、サーバーの起動時に自動で起動する | systemd |
| 複数台 | コンテナ | どのサーバーで動かすかを決める、サーバーごと止まっても別のサーバーで起動し直す、数の増減、入れ替え | Kubernetes、ECS |

1台の中の管理（systemd）では、サーバー自体が止まったときは何もできません。複数台をまとめて管理する仕組みは、それぞれのサーバーの空き CPU・メモリと、動いているものを常に把握していて、止まったサーバーの分を別のサーバーで起動し直します。

### systemd での例

```ini
[Service]
ExecStart=/opt/app/server
Restart=always        # 落ちたら起動し直す
RestartSec=3          # 3 秒待ってから
User=appuser
MemoryMax=1G          # メモリの上限
```

## 設計で決めること

### 1. どの範囲で管理するか
- 選択肢：1台の中でプロセスを管理する（systemd）／複数台でコンテナを管理する（Kubernetes、ECS）
- 判断の基準：サーバーが1〜2台で増減もしないなら systemd で足りる。台数が多い、アクセスに合わせて増減させたい、サーバーが止まっても自動で戻したいなら、複数台をまとめて管理する仕組みを使う

### 2. 何個動かし、いつ増減させるか
- 選択肢：数を固定する／CPU 使用率やリクエスト数に応じて自動で増減させる（オートスケール）
- 判断の基準：最低でも2個にして、1個止まってもサービスが続くようにする。自動で増やすなら、増えた分の DB の接続数が上限を超えないかも計算する → [[接続プール]]

### 3. 「正常に動いている」をどう判定するか
- 選択肢：プロセスが動いているか／ポートで応答するか／アプリの特定のパスが正しい応答を返すか
- 判断の基準：プロセスが動いていても、固まって応答しないことがある。リクエストを受けるアプリなら、応答を確かめる → [[ヘルスチェック]]

### 4. 1つ分の CPU・メモリの上限をいくつにするか
- 選択肢：上限を決める／決めない
- 判断の基準：上限を決める。決めないと、1つがメモリを使い切ったときに、同じサーバーの他のものまで巻き込む。上限を超えたものは強制終了されるので、普段の使用量に余裕を持たせた値にする

### 5. 状態をどこに置くか
- 選択肢：プロセスやコンテナの中／外（DB、Redis、ファイルの保存先、ログの収集先）
- 判断の基準：外に置く。オーケストレーションは、いつでも止めて別の場所で起動し直す前提で動く。中に置いたファイルやセッションは、そのときに消える

### 6. 止めるときに、どれだけ待つか
- 選択肢：止める合図（SIGTERM）を送ってから、強制終了（SIGKILL）するまでの猶予時間
- 判断の基準：一番長いリクエストの処理時間より長くする。アプリ側も、合図を受けたら処理中を終えてから終了する → [[グレースフルシャットダウン]]

## 障害

| 症状 | 原因 | 確かめ方 |
|---|---|---|
| 起動してはすぐ止まる、を繰り返す | 起動時のエラー（設定の不足、接続先に繋がらない）、正常の判定に通らない | オーケストレーションが記録している「止まった理由」と、アプリの起動時のログを見る |
| 終了コード 137 で止まる | 強制終了（SIGKILL）された。多くはメモリの上限を超えた | メモリの使用量の推移を見る。じわじわ増えているならメモリリークを疑う |
| 「時々エラー」が出るが、見に行くと正常 | 落ちては自動で起動し直している | プロセスやコンテナの起動時刻と、再起動の回数を見る。自動で戻るので、落ちていることに気づきにくい |
| 新しい版に入れ替わらない | 新しい版が正常の判定に通らない、空いている CPU・メモリが足りない | 新しい版の起動時のログと、サーバーの空き資源を見る |

## 実行モデルで変わること
→ [[実行モデル]]

| | 作り直す型（PHP-FPM） | 常駐型（Go など） |
|---|---|---|
| 管理するプロセス | Nginx と PHP-FPM の2つ（コンテナなら2つを組にする） | アプリのプロセス1つで済むことが多い |
| メモリの上限の見積もり | worker 数 × worker 1つのメモリ | プロセスのメモリの増え方（同時処理数で変わる）を見る |
| 落ちたときの影響 | worker 1つなら影響は小さい | プロセスが落ちると全部のリクエストが失敗する。自動で起動し直す仕組みが特に大事 |
