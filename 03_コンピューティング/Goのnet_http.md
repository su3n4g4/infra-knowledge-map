# Go の net/http

Go の標準ライブラリに含まれる HTTP サーバー。Go のプロセス自身がポート（8080 番など）で待ち受け、リクエストごとに goroutine を立てて同時に処理する。常駐型のアプリケーションサーバーの代表 → [[実行モデル]]

## なぜ必要か

PHP では「Nginx が受けて、PHP-FPM の worker が処理する」という2つのプロセスの分担が必要でした。Go では、**コンパイルしたバイナリ自体が HTTP サーバー** です。Nginx も PHP-FPM も要らず、1つのプロセスで完結します。

その代わり、PHP では Nginx や PHP-FPM が引き受けていた **タイムアウトや同時処理数の制限を、自分のコードで設定する** 必要があります。

## 仕組み

### 1つのプロセスの中で、たくさんの goroutine が動く

```txt
           1つの Go プロセス
 ┌──────────────────────────────────┐
 │ net/http サーバー（:8080 で待ち受け） │
 │   ├ リクエスト1 → goroutine         │
 │   ├ リクエスト2 → goroutine         │  ← 自動で立つ
 │   └ リクエスト3 → goroutine         │
 │                                  │
 │ GOMAXPROCS 個の OS スレッドの上で動く │
 └──────────────────────────────────┘
               │ sql.DB（接続プール）
               ▼
             DB サーバー
```

- **goroutine**：Go のランタイムが管理する軽いスレッド。数 KB から始まるので、数万本でも立てられる
- **OS から見えるのはプロセスとスレッドまで**。goroutine は Go の中だけの存在なので、`top` では見えない
- DB やネットワークの応答を待っている goroutine は OS スレッドから外され、そのスレッドでは別の goroutine が実行される。だから待ち時間があっても CPU を遊ばせない

### GOMAXPROCS（同時に CPU で動ける数）

goroutine が何本あっても、**同時に CPU 上で動けるのは GOMAXPROCS 個まで** です。

- Go 1.24 までは、コンテナの CPU の上限を見ずに、ホスト全体の CPU 数を初期値にしていた。2コアに制限したコンテナで 64 個のスレッドを動かそうとし、切り替えの無駄でかえって遅くなることがあった
- Go 1.25 からは、Linux では cgroup の CPU の上限を見て初期値を決める。それより前の Go では、`go.uber.org/automaxprocs` を入れて合わせる

## 設計で決めること

### 1. タイムアウトをどう設定するか
- 選択肢：`http.Server` の `ReadHeaderTimeout` / `ReadTimeout` / `WriteTimeout` / `IdleTimeout`
- 判断の基準：**必ず設定する**。`http.ListenAndServe` をそのまま使うと無制限になり、遅い（または悪意のある）クライアントが接続を握り続け、goroutine とメモリを食いつぶす。`IdleTimeout` は手前のロードバランサーのタイムアウトより長くする

```go
srv := &http.Server{
    Addr:              ":8080",
    Handler:           mux,
    ReadHeaderTimeout: 5 * time.Second,
    ReadTimeout:       10 * time.Second,
    WriteTimeout:      30 * time.Second,
    IdleTimeout:       120 * time.Second,
}
```

### 2. 同時に処理する数を制限するか
- 選択肢：制限しない（net/http の初期の動き）／セマフォなどで上限を設ける
- 判断の基準：net/http は goroutine を上限なく立てる。アクセスが急に集中する可能性があり、1リクエストのメモリが大きいなら、上限を設ける

### 3. GOMAXPROCS を CPU の上限と合わせるか
- 選択肢：Go 1.25 以降の初期値に任せる／`automaxprocs` で合わせる／手で設定する
- 判断の基準：コンテナで CPU を制限しているなら、Go のバージョンを確かめる。1.24 以前なら `automaxprocs` を入れる

### 4. 止め方
- 選択肢：何もしない（すぐ終了）／`Shutdown` を呼んで処理中を待つ
- 判断の基準：処理中を待つ → [[グレースフルシャットダウン]]

## 障害

| 症状 | 原因 | 確かめ方 |
|---|---|---|
| じわじわメモリが増えて落ちる | 終わらない goroutine が溜まっている（goroutine リーク） | `net/http/pprof` で goroutine の数の推移と、どこで止まっているかを見る |
| アクセスの集中でメモリを使い切る | goroutine が上限なく増えた | 同時に処理している数を絞る |
| CPU を増やしても速くならない | GOMAXPROCS がコンテナの CPU の上限と合っていない | `runtime.GOMAXPROCS(0)` の値と、コンテナの CPU の上限を比べる |
| 時々 502 | プロセスが落ちて再起動している | ログで `panic:` を探す → [[panicとrecover]] |

## 実行モデルで変わること
→ [[実行モデル]]

| | 作り直す型（PHP-FPM） | 常駐型（Go など） |
|---|---|---|
| HTTP を受けるもの | Nginx | アプリのプロセス自身 |
| 同時処理の上限 | `pm.max_children` | なし（自分で決める） |
| タイムアウトを持つ場所 | Nginx・PHP-FPM の設定 | `http.Server` の設定（コード） |

Node.js も同じ常駐型ですが、1本のスレッドで処理を切り替えるので、重い計算をすると他のリクエストが止まります。
