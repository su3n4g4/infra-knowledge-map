# panic と recover

panic は、Go のプログラムが処理を続けられない異常（nil の参照など）を起こしたときの停止の仕組み。`recover` で受け止めないと、panic を起こした goroutine だけでなく、Go のプロセス全体が終了する。

## なぜ問題か

作り直す型（PHP-FPM）では、1つのリクエストで致命的なエラーが起きても、困るのはその worker が処理していたリクエストだけです。ほかの worker は別のプロセスなので影響を受けません。

Go は **1つのプロセスで全リクエストを処理** します（常駐型 → [[実行モデル]]）。どこかの goroutine で panic が起き、誰も受け止めないと、**プロセス全体が終了** し、同時に処理中だった他のリクエストもすべて失敗します。

```txt
PHP-FPM：1リクエストのエラー → その worker が死ぬだけ
Go     ：1リクエストの panic → プロセスが死ぬ → 全リクエストが死ぬ
```

さらに、落ちたプロセスはオーケストレーションが数秒で起動し直すので、症状は「**時々エラー**」に化け、気づきにくくなります。

## 起きる仕組み

### panic が起きる場面

- nil のポインタやマップにアクセスした
- 配列の範囲外にアクセスした
- コードの中で明示的に `panic()` を呼んだ

### net/http が守ってくれる範囲と、守ってくれない範囲

`defer` の中で `recover()` を呼ぶと、その goroutine で起きた panic を受け止め、プロセスの終了を防げます。ただし、`recover` が効くのは **同じ goroutine の中だけ** です。

```go
func handler(w http.ResponseWriter, r *http.Request) {
    // ① ここでの panic は net/http が受け止める（その接続だけが切れる）

    go func() {
        // ② ここでの panic は誰も受け止めない → プロセスごと落ちる
        sendMail()
    }()
}
```

ハンドラの中で `go func()` を立てて別の goroutine を作ると、その中の panic は net/http が受け止める範囲の外になります。

## 前後のつながり

[[ロードバランサー]] → [[Goのnet_http]]（**ここで panic が起きる**）→ プロセスが落ちる → [[オーケストレーション]] が起動し直す

## 見つけ方

| 症状 | 確かめ方 |
|---|---|
| 時々 502 が出る | ログで `panic:` とスタックトレースを探す。ネットワークの不調と誤解しやすい |
| プロセスの起動時刻が、デプロイした時刻より新しい | 落ちては起動し直している証拠。オーケストレーションの停止の理由と再起動の回数を見る |

panic のスタックトレースは標準エラーに出るので、ログが集められていないと原因を追えません。

## 直し方

### 1. 自分で立てた goroutine には、必ず recover を書く
- どうするか：

```go
go func() {
    defer func() {
        if r := recover(); r != nil {
            log.Printf("panic: %v", r)
        }
    }()
    sendMail()
}()
```

- 使う場面：`go func()` を書くとき、毎回。習慣にする

### 2. 全ハンドラの手前に、recover するミドルウェアを置く
- どうするか：panic をログに残し、500 を返すミドルウェアを、すべてのハンドラの手前に置く
- 使う場面：panic の内容を、自分の決めた形でログに残したいとき

### 3. 落ちても自動で起動し直すようにしておく
- どうするか：systemd の `Restart=always` や、オーケストレーションの自動の再起動を設定する
- 使う場面：上の2つで防ぎきれなかったときの備えとして、常に。ただし、これだけに頼ると落ちていることに気づかないので、再起動の回数を監視する
