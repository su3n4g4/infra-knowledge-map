# ECS（Elastic Container Service）

AWS が提供するコンテナのオーケストレーションのサービス。「このイメージのコンテナを N 個」という指定を受け、EC2 または Fargate の上でコンテナを起動し、止まったものを起動し直して、指定どおりの数を保つ。

仕組みと設計の考え方は [[オーケストレーション]] にまとめています。この解説では、**ECS に固有の部品・初期値・動き** だけを扱います。

## なぜ必要か

Kubernetes を自分で運用すると、Kubernetes 自体を動かすサーバーの管理や更新も自分で持つことになります。ECS を使うと、その部分を AWS に任せられます。

- 管理の仕組み自体を運用しなくてよい
- ALB、ECR、CloudWatch、IAM など AWS の他のサービスとつなぐ設定が少ない
- Fargate を選べば、コンテナを動かすサーバー（EC2）の管理も要らない

覚えることは Kubernetes より少なく済みます。その代わり、AWS の外には持ち出せません。

## 概念との対応

| オーケストレーションの概念 | ECS での名前 |
|---|---|
| 動かすものの設計図（イメージ、CPU、メモリ、ポート、環境変数） | タスク定義 |
| 動いている1つ分 | タスク（1つのタスクに複数のコンテナを入れられる） |
| 「N 個動かす」という指定と、それを保つ仕組み | サービス（希望するタスク数） |
| 動かす場所のまとまり | クラスター |
| 動かす場所 | 起動タイプ：EC2 または Fargate |
| 数の自動の増減 | サービスの Auto Scaling |
| 新旧の入れ替え | サービスのデプロイ設定 |

```txt
クラスター
 └ サービス「web」：希望するタスク数 4
     ├ タスク（タスク定義 web:12）
     │    ├ コンテナ nginx  :80
     │    └ コンテナ php-fpm :9000   ← 同じタスクの中は localhost でつながる
     ├ タスク
     ├ タスク
     └ タスク
```

### 起動タイプ

| 起動タイプ | コンテナを動かすサーバー | 向いている場面 |
|---|---|---|
| EC2 | 自分で用意した EC2。OS の更新や台数の管理も自分で行う | GPU など特殊なサーバーが要る、大量のタスクを安く動かしたい |
| Fargate | AWS が用意する。自分はタスクに CPU とメモリを指定するだけ | サーバーの管理をしたくない。多くの Web アプリ |

## 初期値と変える値

| 設定 | 初期値 | 何に効くか | 変える目安 |
|---|---|---|---|
| 最小ヘルス率 | 100% | 入れ替え中も、希望数の何%は動かし続けるか | 余分に起動する資源が無いなら下げる（その間は処理能力が落ちる） |
| 最大率 | 200% | 入れ替え中、希望数の何%まで一時的に増やしてよいか | 一度に入れ替える数を減らしたいなら下げる |
| 停止までの猶予（stopTimeout） | 30 秒 | SIGTERM から SIGKILL までの時間 | 処理に時間のかかるリクエストやジョブがあるなら延ばす（Fargate は最大 120 秒） |
| ヘルスチェックの猶予期間 | 0 秒 | 起動直後、ALB のヘルスチェックの失敗を無視する時間 | 起動に時間がかかるアプリは、起動中に失敗と判定されて止められるので延ばす |
| デプロイメントサーキットブレーカー | 作成方法による | 新しい版が起動に失敗し続けたら、デプロイを止めて前の版に戻す | 有効にして、自動で戻すようにする |

## 実装に固有の動き

### ALB への登録・解除を自動で行う
サービスに ALB のターゲットグループを指定すると、タスクが起動するたびに IP:ポートを登録し、止めるときは先に登録を解除します。登録解除の遅延（ALB の初期値 300 秒）を待ってから、SIGTERM を送ります → [[ALB]]

### 止まった理由が記録される
止まったタスクの「停止理由」と、コンテナの終了コードが、ECS の画面に一定期間残ります。終了コード 137 は SIGKILL で終了したことを表し、多くはメモリの上限超えです。

### 2つのロール
ECS には役割の違う IAM ロールが2つあります。

| ロール | 誰が使うか | 主な権限 |
|---|---|---|
| タスク実行ロール | ECS 自身 | ECR からイメージを取得する、ログを CloudWatch Logs に送る、Secrets Manager から秘密情報を取り出す |
| タスクロール | コンテナの中のアプリ | アプリが S3 などの AWS のサービスを使う |

イメージを取得できないときは実行ロール、アプリが S3 に書けないときはタスクロールを見ます。

### EC2 起動タイプでは ecs-agent が動く
EC2 起動タイプでは、各 EC2 で `ecs-agent` というプロセスが動き、空いている CPU・メモリと動いているコンテナを ECS に報告しています。agent が止まると、その EC2 にはタスクが置かれなくなります。

## 障害

| 症状 | 原因 | 確かめ方 |
|---|---|---|
| タスクが起動しない（イメージを取得できない） | 実行ロールに ECR の権限が無い、プライベートサブネットから ECR へ出る経路（NAT か VPC エンドポイント）が無い | 停止理由に `CannotPullContainerError` が出る |
| 起動直後に止められる、を繰り返す | ヘルスチェックの猶予期間が短く、起動中に失敗と判定された | 停止理由が「ELB のヘルスチェックに失敗」なら、猶予期間とアプリの起動時間を比べる |
| 秘密情報を読めず起動しない | 実行ロールに Secrets Manager の権限が無い | 停止理由に `ResourceInitializationError` が出る |
| デプロイが終わらない | 新しいタスクが正常にならない、Fargate の資源が一時的に足りない | サービスの「イベント」タブに、何を待っているかが出る |
