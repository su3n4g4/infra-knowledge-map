# infra-knowledge-map

インフラと設計の知識を、**1つの技術を学ぶ「解説」** と、解説どうしのつながりをたどる **「マップ」** に分けてまとめたノート。
「用語は知っているが、何がどうつながっているか説明できない」状態から、全体の流れの中で1つずつ理解することを目指す。

## 使い方

**Obsidian で開いて使うノート** です。リンクは Obsidian の `[[名前]]` の形で書いているため、GitHub の画面上ではリンクとして動かず、キャンバス（`.canvas`）も図として表示されません。

1. このフォルダを Obsidian の保管庫に入れる（保管庫のどこに置いてもよい。リンクはファイル名で指しているので、フォルダの位置は関係しない）
2. `_maps/00_全体マップ.md` を開く。場面（理解する／作業する／困った）と疑問から、進むマップを選べる

### GitHub で読むとき

マップの説明ページ（`.md`）は、表と Mermaid の図で書いているので GitHub でも読めます。入口は次のとおりです。

| 知りたいこと | 説明ページ |
|---|---|
| どこから読めばよいか | [全体マップ](_maps/00_全体マップ.md) |
| リクエストはどう進むか | [1リクエストの流れ](_maps/1リクエストの流れ.md) |
| デプロイはどう進むか | [デプロイの流れ](_maps/デプロイの流れ.md) |
| 各部品はどの層で動くか | [OSI参照モデルとリクエスト](_maps/OSI参照モデルとリクエスト.md) |
| オンプレではどこに置くか | [オンプレ構成](_maps/オンプレ構成.md) |
| AWS ではどこに置くか | [AWS構成](_maps/AWS構成.md) |
| 障害のときどこを見るか | [障害の切り分け](_maps/障害の切り分け.md) |

説明ページの中のリンクは `[[名前]]` の形なので、解説へは上の「フォルダ」から同じ名前のファイルを開いてください。

## フォルダ

| フォルダ | 中身 |
|---|---|
| `_maps/` | マップ。図（`.canvas`）と説明ページ（`.md`） |
| `01_基礎/` | 土台の考え方（実行モデルなど） |
| `02_ネットワーク/` | DNS、TLS、ロードバランサーなど |
| `03_コンピューティング/` | アプリケーションサーバー、オーケストレーションなど |
| `04_データ/` | データベースサーバー、接続プールなど |
| `05_配布/` | CI、コンテナレジストリ、デプロイの方式など |
| `06_監視/` | ヘルスチェックなど |
| `07_セキュリティ/` | （これから） |
| `_templates/` | 解説のひな形（種類ごと） |

解説は、技術の分類ごとのフォルダに置く。ファイル名は技術の名前だけにする（頭に番号や分類を付けない）。

## マップ

### 一覧

| マップ | 示すもの | 視点 | 環境 |
|---|---|---|---|
| 1リクエストの流れ | URL を開いてからレスポンスが返るまでの順番 | 流れ | 共通 |
| デプロイの流れ | push してから新しい版に入れ替わるまでの順番 | 流れ | 共通 |
| OSI参照モデルとリクエスト | 各部品が、どの層で何をしているか | 層 | 共通 |
| オンプレ構成 | 自分たちのサーバーで組むときの置き場所と通信の制限 | 配置 | オンプレ |
| AWS構成 | AWS で組むときの置き場所と通信の制限 | 配置 | AWS |
| 障害の切り分け | 症状から、どこを疑えばよいか | 逆引き | 共通 |

視点と環境は、各マップの先頭の属性（`視点:`、`環境:`）に書いている。

### 決まり

- **環境で変わるのは「配置」だけ**。流れ・層・逆引きのマップは、オンプレでも AWS でも同じなので共通にする
- 共通のマップは、概念の解説（ロードバランサーなど）にリンクする
- 配置のマップは環境ごとに作る。AWS の配置は実装の解説（ALB など）にリンクし、そこから概念の解説へたどる
- 言語やフレームワークに固有のもの（PHP-FPM、Go の net/http など）はマップに置かない。「アプリケーションサーバー」と書き、[実行モデル](01_基礎/実行モデル.md) の解説へ案内する

### 1枚のマップの形

すべてのマップを、図と説明ページの2つで持つ。

**図（`.canvas`）**
- 冒頭の箱：マップの名前と、「〜を示すマップ。」という1文、説明ページへのリンク
- 解説を指す箱：`### [[解説の名前]]` と、その下に1文の説明だけを書く
- Obsidian で開く。GitHub では図として表示されない

**説明ページ（`.md`）**
- 文章の解説は書かず、表とリンクだけにする（説明は解説に任せる）
- GitHub で見るときや、AI に渡すときはこちらを使う
- 見出しは次の順番にそろえる

| 見出し | 中身 |
|---|---|
| （見出しなし） | 「〜を示すマップ。」という1文と、図へのリンク |
| 全体図 | 図と同じ中身の Mermaid |
| ○○と解説 | マップの中身の表。最後の列に解説へのリンク。○○はマップに合わせる（順番・層・置き場所・症状） |
| （必要なら追加の表） | 例：通信の制限、AWS 構成との対応 |
| あわせて見るマップ | 「知りたいこと → マップ」の形で書く |

## 解説

### 種類

解説は、性質によって種類を分け、種類ごとのテンプレートを使う。先頭の `種類:` に書く。

| 種類 | 何を書くか | 例 | テンプレート |
|---|---|---|---|
| 概念 | オンプレでも AWS でも通じる仕組みと考え方 | ロードバランサー、接続プール | `_templates/解説_概念.md` |
| 実装 | 概念を特定の環境で実現するもの。その環境に固有のことだけ | ALB、RDS | `_templates/解説_実装.md` |
| 問題 | 避けるべき書き方や状態と、その見つけ方・直し方 | N+1問題 | `_templates/解説_問題.md` |
| 判断 | 2つのどちらを選ぶかの基準と手順 | ロールバック判断 | `_templates/解説_判断.md` |
| 考え方 | ものごとを型に分けて見る観点 | 実行モデル | `_templates/解説_考え方.md` |

### 見出し

全種類に共通：

- 冒頭の定義（見出しなし。たとえを使わず、プロセス・ポート・IP など実際に動くものの言葉で書く）
- なぜ必要か（問題では「なぜ問題か」）
- 前後のつながり
- 関連する解説

種類ごと：

| 種類 | 見出し |
|---|---|
| 概念 | 仕組み、設計で決めること、障害、実行モデルで変わること（違いがあるときだけ）、実装の例 |
| 実装 | 概念との対応、初期値と変える値、実装に固有の動き、障害（その実装に固有のものだけ） |
| 問題 | 起きる仕組み、見つけ方、直し方 |
| 判断 | 判断の基準、手順、事前の備え |
| 考え方 | 仕組み、比較、当てはめ方 |

### 粒度のルール

見出しごとに、1項目で何を1つ書くかを決めている。

| 見出し | 1項目＝ | 必ず書くこと |
|---|---|---|
| 設計で決めること | 1つの決定 | 選択肢、判断の基準 |
| 障害 | 1つの症状 | 症状、原因、確かめ方 |
| 初期値と変える値 | 1つの設定 | 初期値、何に効くか、変える目安 |
| 実装に固有の動き | 1つの動き | 概念の説明からは予想できない点 |
| 見つけ方 | 1つの症状 | 症状、確かめ方 |
| 直し方 | 1つの方法 | どうするか、使う場面 |
| 判断の基準 | 1つの基準 | どちらに傾くか |
| 事前の備え | 1つの備え | 何をしておくか、何が楽になるか |
| 当てはめ方 | 1つの場面 | 見分け方、気をつけること |

### 属性

| 属性 | 値 |
|---|---|
| `type` | `解説` |
| `種類` | `概念` / `実装` / `問題` / `判断` / `考え方` |
| `分類` | フォルダと同じ分類（ネットワーク、データなど） |
| `小分類` | 分類の中の区分（負荷分散、RDB など） |

### 事実の確認

AWS の初期値や、Nginx・PHP-FPM・Go などの設定値は、2026年11月時点の公式ドキュメントで確かめている。サービスやソフトウェアの更新で変わることがあるので、使う前に最新のドキュメントも確かめる。
