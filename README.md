# infra-knowledge-map

インフラと設計の知識を、**1つの技術を学ぶ「解説」** と、解説どうしのつながりをたどる **「マップ」** に分けてまとめたノート。
「用語は知っているが、何がどうつながっているか説明できない」状態から、全体の流れの中で1つずつ理解することを目指す。

## 使い方

**Obsidian で開いて使うノート** です。リンクは Obsidian の `[[名前]]` の形で書いているため、GitHub の画面上ではリンクとして動かず、図（キャンバス `.canvas`、Excalidraw `.excalidraw.md`）も図として表示されません。

1. このフォルダを Obsidian の保管庫に入れる（保管庫のどこに置いてもよい。リンクはファイル名で指しているので、フォルダの位置は関係しない）
   - 図の一部は Excalidraw で描いている。コミュニティプラグイン「Excalidraw」を入れる
   - Excalidraw の図を Obsidian のライト／ダークに合わせるには、プラグインの設定（Excalidraw appearance and behavior → Theme and styling）で「Existing drawings to match Obsidian theme」と「Excalidraw to follow when Obsidian Theme changes」をオンにする。図のファイルには背景の色を決め打ちで書かない
2. `_maps/00_全体マップ.md` を開く。場面（理解する／作業する／困った）と疑問から、進むマップを選べる

### GitHub で読むとき

マップの説明ページ（`.md`）は、表と Mermaid の図で書いているので GitHub でも読めます。入口は次のとおりです。

| 知りたいこと | 説明ページ |
|---|---|
| どこから読めばよいか | [全体マップ](_maps/00_全体マップ.md) |
| リクエストはどう進むか | [1リクエストの流れ](_maps/1リクエストの流れ.md) |
| デプロイはどう進むか | [デプロイの流れ](_maps/デプロイの流れ.md) |
| 各部品はどの層で動くか | [OSI参照モデルとリクエスト](_maps/OSI参照モデルとリクエスト.md) |
| オンプレではどこに置くか | [オンプレ構成](_maps/オンプレ構成.md) |
| AWS ではどこに置くか | [AWS構成](_maps/AWS構成.md) |
| docker compose ではどこに置くか | [Docker compose構成](_maps/Docker%20compose構成.md) |
| コンテナは何でできているか | [コンテナの仕組み](_maps/コンテナの仕組み.md) |
| 障害のときどこを見るか | [障害の切り分け](_maps/障害の切り分け.md) |

説明ページの中のリンクは `[[名前]]` の形なので、解説へは上の「フォルダ」から同じ名前のファイルを開いてください。

## マップ

### 一覧

| マップ | 示すもの | 視点 | 環境 |
|---|---|---|---|
| 1リクエストの流れ | URL を開いてからレスポンスが返るまでの順番 | 流れ | 共通 |
| デプロイの流れ | push してから新しい版に入れ替わるまでの順番 | 流れ | 共通 |
| OSI参照モデルとリクエスト | 各部品が、どの層で何をしているか | 層 | 共通 |
| オンプレ構成 | 自分たちのサーバーで組むときの置き場所と通信の制限 | 配置 | オンプレ |
| AWS構成 | AWS で組むときの置き場所と通信の制限 | 配置 | AWS |
| Docker compose構成 | 手元で docker compose を使うときの置き場所と通信の制限 | 配置 | ローカル |
| コンテナの仕組み | コンテナが、カーネルのどの機能の上に、どの部品で作られているか | 層 | 共通 |
| 障害の切り分け | 症状から、どこを疑えばよいか | 逆引き | 共通 |

視点と環境は、各マップの先頭の属性（`視点:`、`環境:`）に書いている。

### 決まり

- **環境で変わるのは「配置」だけ**。流れ・層・逆引きのマップは、オンプレでも AWS でも同じなので共通にする
- 共通のマップは、概念の解説（ロードバランサーなど）にリンクする
- 配置のマップは環境（オンプレ・AWS・ローカル）ごとに作る。AWS の配置は実装の解説（ALB など）にリンクし、そこから概念の解説へたどる
- 言語やフレームワークに固有のもの（PHP-FPM、Go の net/http など）はマップに置かない。「アプリケーションサーバー」と書き、[実行モデル](01_基礎/実行モデル.md) の解説へ案内する

### 1枚のマップの形

すべてのマップを、図と説明ページの2つで持つ。

**図**

図は Obsidian のキャンバス（`.canvas`）か Excalidraw（`.excalidraw.md`）のどちらかで描く。1枚のマップに図は1つ。説明ページからは `[[名前.canvas]]` か `[[名前.excalidraw]]` でリンクする。

- 冒頭の文字：マップの名前と、「〜を示すマップ。」という1文、説明ページへのリンク
- 解説を指す箱：解説へのリンクと、その下に1文の説明だけを書く（キャンバスは `### [[解説の名前]]`、Excalidraw は見出しの記号が使えないので `[[解説の名前]]` の1行目）
- 図が指す解説と、説明ページの表が指す解説は、必ず同じにする。片方にだけ足さない
- まだ解説が無い部品も `[[名前]]` で書く。Obsidian で未作成のリンクとして色が変わり、空いている場所が見える。そのときは [全体マップ](_maps/00_全体マップ.md) の「これから書く解説」に名前を足す（足さないと、点検でリンク切れになる）
- Obsidian で開く。GitHub では図として表示されない

| | キャンバス（`.canvas`） | Excalidraw（`.excalidraw.md`） |
|---|---|---|
| 向くもの | 箱と矢印だけの図 | 手で描き足したい図、入れ子が多い図 |
| 分類の枠 | group | frame（入れ子にできないので、内側の区切りは破線の四角） |
| 色 | 利用者・外部 `"5"`、制限 `"1"`、注意書き `"4"` | 利用者・外部 `#99e9f2`、制限 `#ffc9c9`、注意書き `#b2f2bb` |
| リンクの置き場所 | 箱の text | 文字の要素。ファイルの `## Text Elements` に書かれ、点検はここを読む |

**説明ページ（`.md`）**
- 文章の解説は書かず、表とリンクだけにする（説明は解説に任せる）
- GitHub で見るときや、AI に渡すときはこちらを使う
- 見出しは次の順番にそろえる

| 見出し | 中身 |
|---|---|
| （見出しなし） | 「〜を示すマップ。」という1文と、図へのリンク |
| 全体図 | 図と同じ中身の Mermaid |
| ○○と解説 | マップの中身の表。最後の列に解説へのリンク。○○はマップに合わせる（順番・層・置き場所・症状） |
| （必要なら追加の表） | 例：通信の制限、AWS 構成との対応 |
| あわせて見るマップ | 「知りたいこと → マップ」の形で書く |

## 解説

### 種類

解説は、性質によって種類を分け、種類ごとのテンプレートを使う。先頭の `種類:` に書く。

| 種類 | 何を書くか | 例 | テンプレート |
|---|---|---|---|
| 概念 | オンプレでも AWS でも通じる仕組みと考え方 | ロードバランサー、接続プール | `_templates/解説_概念.md` |
| 実装 | 概念を特定の環境で実現するもの。その環境に固有のことだけ | ALB、RDS | `_templates/解説_実装.md` |
| 問題 | 避けるべき書き方や状態と、その見つけ方・直し方 | N+1問題 | `_templates/解説_問題.md` |
| 判断 | 2つのどちらを選ぶかの基準と手順 | ロールバック判断 | `_templates/解説_判断.md` |
| 考え方 | ものごとを型に分けて見る観点 | 実行モデル | `_templates/解説_考え方.md` |

### 見出し

全種類に共通：

- 冒頭の定義（見出しなし。たとえを使わず、プロセス・ポート・IP など実際に動くものの言葉で書く）
- なぜ必要か（問題では「なぜ問題か」）
- 前後のつながり（下の「前後のつながり」の決まりで書く）
- 関連する解説（ここに書いた相手の解説からも、こちらへリンクする）

### 前後のつながり

解説から、その解説が全体のどこにあるかへ戻るための見出し。**載っているマップごとに1行** 書く。

```markdown
- [[1リクエストの流れ]]（④）：[[DNS]] → [[CDN]] → **ロードバランサー** → [[Nginx]]
- [[オンプレ構成]]（DMZ）：ファイアウォールの内側で 443 を受ける
- [[障害の切り分け]]：「502 / 503 / 504」のときに疑う
```

| マップの視点 | 括弧の中 | コロンの後 |
|---|---|---|
| 流れ | 順番（①など） | 前後の解説を矢印でつなぐ。自分は太字 |
| 層 | 層（L7 など） | その層で何をしているか |
| 配置 | 置き場所 | 何の隣にあり、どこから届くか |
| 逆引き | （なし） | どの症状のときに疑うか |

- マップの表に載っていれば、そのマップの行を必ず書く。載っていないマップの行は書かない
- 言語やフレームワークに固有のもので、マップに載らない解説は、`マップには直接載らない（[[実行モデル]] の「常駐型」として載る）：…` の1行にする

種類ごと：

| 種類 | 見出し |
|---|---|
| 概念 | 仕組み、設計で決めること、障害、実行モデルで変わること（違いがあるときだけ）、実装の例 |
| 実装 | 概念との対応、初期値と変える値、実装に固有の動き、障害（その実装に固有のものだけ） |
| 問題 | 起きる仕組み、見つけ方、直し方 |
| 判断 | 判断の基準、手順、事前の備え |
| 考え方 | 仕組み、比較、当てはめ方 |

### 粒度のルール

見出しごとに、1項目で何を1つ書くかを決めている。

| 見出し | 1項目＝ | 必ず書くこと |
|---|---|---|
| 設計で決めること | 1つの決定 | 選択肢、判断の基準 |
| 障害 | 1つの症状 | 症状、原因、確かめ方 |
| 初期値と変える値 | 1つの設定 | 初期値、何に効くか、変える目安 |
| 実装に固有の動き | 1つの動き | 概念の説明からは予想できない点 |
| 見つけ方 | 1つの症状 | 症状、確かめ方 |
| 直し方 | 1つの方法 | どうするか、使う場面 |
| 判断の基準 | 1つの基準 | どちらに傾くか |
| 事前の備え | 1つの備え | 何をしておくか、何が楽になるか |
| 当てはめ方 | 1つの場面 | 見分け方、気をつけること |

### 属性

| 属性 | 値 |
|---|---|
| `type` | `解説` |
| `種類` | `概念` / `実装` / `問題` / `判断` / `考え方` |
| `分類` | フォルダと同じ分類（ネットワーク、データなど） |
| `小分類` | 分類の中の区分。下の表の値から選ぶ |
| `確認日` | 事実を公式ドキュメントで確かめた日（`2026-11` か `2026-11-15` の形） |

### 小分類

使ってよい値の一覧。新しい区分が要るときは、先にこの表に足す。

| 分類 | 小分類 |
|---|---|
| 基礎 | 実行モデル |
| ネットワーク | 名前解決、CDN、通信の暗号化、負荷分散 |
| コンピューティング | Web・アプリサーバー、オーケストレーション |
| データ | RDB |
| 配布 | CI、成果物の保管、DB マイグレーション、デプロイ方式 |
| 監視 | ヘルスチェック |
| セキュリティ | （これから） |

### 事実の確認

AWS の初期値や、Nginx・PHP-FPM・Go などの設定値は、公式ドキュメントで確かめて書き、確かめた日を属性の `確認日` に入れる。サービスやソフトウェアの更新で変わることがあるので、確認日が古い解説を使う前は、最新のドキュメントも確かめる。

## 更新のしかた

### Claude Code で更新する

このフォルダを Claude Code で開き、`/update-notes` に新しく知ったことを渡す。

```txt
/update-notes ALB のアイドルタイムアウトの初期値は 60 秒で、最大 4000 秒まで変えられる
```

既存の解説への追記か新しい解説かを判断し、解説・関連する解説・マップ（表・Mermaid・図）・全体マップをまとめて更新し、最後に点検する。手順は [.claude/skills/update-notes/SKILL.md](.claude/skills/update-notes/SKILL.md) にある。

### 点検

手で直したときも、次を実行して決まりを守れているか確かめる。Node.js が要る。

```txt
node scripts/check.js
```

| 点検すること | 例 |
|---|---|
| 属性がそろっているか | 種類・分類・小分類・確認日の空欄、分類とフォルダの不一致、表に無い小分類 |
| リンク切れが無いか | 行き先の無い `[[名前]]` |
| 図と説明ページが同じ解説を指しているか | 図にだけ箱がある解説（キャンバスと Excalidraw の両方） |
| まだ書いていない解説 | 全体マップの「これから書く解説」にある名前は、リンク切れにせず「注意」として出す |
| すべての解説が全体マップに載っているか | 新しく足した解説の載せ忘れ |
| 前後のつながりが、載っているマップを全部指しているか | マップに足したのに、解説の側に行が無い |
| 関連する解説が相互にリンクしているか | A の関連する解説に B があるのに、B から A へのリンクが無い |
