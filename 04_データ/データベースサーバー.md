# データベースサーバー

MySQL や PostgreSQL などの DB を動かすサーバー。アプリから TCP（MySQL なら 3306 番）で接続を受け、SQL を実行してデータを保存・検索する。オンプレでは自分で用意したサーバーで、AWS では RDS で動かす。

## なぜ必要か

アプリのサーバーは、台数を増やしたり入れ替えたりできる「使い捨て」にしたい存在です。一方、データは **消えたら取り返しがつきません**。この2つを同じサーバーに置くと、次のことが起きます。

- アプリと DB が CPU とメモリを奪い合う
- アプリのサーバーを増やすと、DB も分かれてしまい、データがそろわない
- アプリのサーバーを入れ替えると、データも一緒に消える

そこで DB を専用のサーバーに分け、すべてのアプリのサーバーがそこにつなぐ形にします。こうすると、アプリは自由に増やしたり入れ替えたりでき、データは1か所で守れます。その代わり、**DB のサーバーが止まると全体が止まる** ので、止まらないための備えと、壊れたときに戻す備えが要ります。

## 仕組み

### アプリとの関係

```txt
[アプリ 1] ─┐
[アプリ 2] ─┼─ TCP :3306 ─▶ [DB サーバー]
[アプリ 3] ─┘                  └ ディスクにデータを保存
```

- アプリは DB に **接続** を張り、その上で SQL を送る。DB が同時に受け付けられる接続の数には上限がある（MySQL の `max_connections`） → [[接続プール]]
- DB は、データをディスクに書いてから「書けた」と返す。だからプロセスが落ちてもデータは残る

### 複製（レプリケーション）

DB のデータを、別のサーバーへ常に写しておく仕組みです。

```txt
[プライマリ] ──変更を送る──▶ [レプリカ]
 読み書き                      読み取り専用
```

| 写し方 | 動き | 良い点 | 困る点 |
|---|---|---|---|
| 非同期 | プライマリは書いたらすぐ返し、あとからレプリカへ送る | 書き込みが速い | プライマリが壊れると、送りきれていない直前の変更が失われることがある。レプリカは少し遅れている |
| 同期 | レプリカにも届いてから返す | 直前の変更も失われない | 書き込みのたびに待つので遅くなる |

複製は2つの目的で使います。

- **切り替え（フェイルオーバー）**：プライマリが止まったら、レプリカをプライマリに昇格させる
- **読み取りの分散**：`SELECT` をレプリカに送り、プライマリの負荷を減らす

### バックアップ

複製は「止まらない」ための備えで、**壊したデータを戻す備えにはなりません**。誤って `DELETE` したら、その操作もレプリカに写るからです。戻すためには、別にバックアップを取ります。

| 方式 | 内容 |
|---|---|
| 定期的な全体の写し | 1日1回など、ある時点のデータを丸ごと保存する |
| 変更の記録（MySQL のバイナリログ） | 全体の写し以降の変更を順に記録する。全体の写しに重ねると、任意の時点に戻せる |

## 設計で決めること

### 1. 止まったときにどう切り替えるか
- 選択肢：切り替えない（復旧を待つ）／同期の複製を用意し、自動で切り替える／非同期の複製を用意し、手動で切り替える
- 判断の基準：止まってよい時間と、失ってよいデータの量で決める。どちらも「ほぼゼロ」が求められるなら、同期の複製と自動の切り替えが要る

### 2. バックアップをどう取り、どこまで戻せるようにするか
- 選択肢：1日1回の全体の写しだけ／全体の写し ＋ 変更の記録で、任意の時点に戻せるようにする
- 判断の基準：「何時何分の状態に戻したいか」をどこまで細かくしたいかで決める。どちらにしても、**戻す手順を一度試しておく**。取れているはずのバックアップから戻せないことは珍しくない

### 3. 読み取りを分散するか
- 選択肢：プライマリだけで読み書きする／読み取りをレプリカに分ける
- 判断の基準：読み取りが多く、プライマリの CPU が足りなくなってきたら分ける。ただしレプリカは少し遅れているので、**書いた直後にその結果を読む処理** はプライマリから読む

### 4. 同時に受け付ける接続の数をいくつにするか
- 選択肢：DB の接続数の上限（`max_connections`）と、アプリ側の接続数の合計
- 判断の基準：アプリ側の接続数 × 台数が、DB の上限を超えないようにする。台数を自動で増やすなら、最大の台数で計算する → [[接続プール]]

### 5. 誰が接続できるようにするか
- 選択肢：インターネットから届く場所に置く／内部のネットワークに置き、アプリのサーバーからだけ届くようにする
- 判断の基準：内部のネットワークに置き、ファイアウォールでアプリのサーバーからの 3306 番だけを許可する。DB を外から直接叩けると、パスワードが漏れた時点でデータを持ち出される

### 6. 遅いクエリをどう見つけるか
- 選択肢：スロークエリログを有効にする／しない
- 判断の基準：有効にする。一定の時間（例：1秒）を超えたクエリが記録され、遅い原因の SQL を特定できる。ただし [[N+1問題]] のように、1つ1つは速いが回数が多いものは、ここには出ない

## 障害

| 症状 | 原因 | 確かめ方 |
|---|---|---|
| `Too many connections` | アプリ側の接続数の合計が、DB の上限を超えた | 「接続数 × 台数」を計算し直す。DB が重いのではなく、設定の問題であることが多い |
| 全体が遅い、DB の CPU が高い | スロークエリ、インデックス不足、[[N+1問題]] | スロークエリログと、クエリの回数を見る |
| 特定の更新だけ止まる | 同じ行を同時に更新していて、ロックを待っている | DB で実行中の処理とロックの待ちを見る（MySQL なら `SHOW PROCESSLIST`） |
| 切り替えのあと、しばらくエラーが続く | アプリが、切れた古い接続を使い続けている | 接続の寿命の設定を見る → [[接続プール]] |
| レプリカから読むと、書いたはずのデータが無い | 複製の遅れ | 書いた直後に読む処理を、プライマリから読むようにする |
| ディスクがいっぱいで書き込めない | データやログの増加 | ディスクの使用量を監視しておく |

## 実行モデルで変わること
→ [[実行モデル]]

| | 作り直す型（PHP-FPM） | 常駐型（Go など） |
|---|---|---|
| DB の接続数 | worker 数 × 台数 | プールの上限 × 台数 |
| 切り替えのあと | 次のリクエストで新しく接続するので、回復が早い | プールに古い接続が残るので、接続の寿命の設定が要る |
