# 接続プール

DB への接続（TCP の接続と認証が済んだもの）を複数本作って保持しておき、リクエストごとに貸し出して使い回す仕組み。Go の `sql.DB` は、接続1本ではなく、このプールを表す。

## なぜ必要か

DB に SQL を送るには、まず接続を張る必要があります。接続を張るには、TCP の接続（3往復のやりとり）と、ユーザー名・パスワードでの認証が要り、毎回やると時間がかかります。

さらに、DB が同時に受け付けられる接続の数には上限（MySQL の `max_connections`）があります。アプリが好き勝手に接続を作ると、上限に当たって新しい接続を断られます。

接続プールは、**作った接続を捨てずに取っておき、次のリクエストに貸し出す** ことで、この2つを解決します。

## 仕組み

```txt
リクエスト ─┐
リクエスト ─┼─▶ プール ──┬ 接続1（使用中）──┐
リクエスト ─┘    （貸し出し）├ 接続2（使用中）──┼─▶ DB サーバー
                         └ 接続3（空き）  ──┘   上限：300
```

- 空いている接続があれば貸す。無ければ、上限まで新しく作る。上限に達していたら、空くまで待たせる
- 使い終わった接続はプールに返し、閉じずに取っておく

### 実行モデルで数え方が違う
→ [[実行モデル]]

**作り直す型（PHP-FPM）**：リクエストが終わると接続も捨てます。通常はプールが無く、**worker 1つが接続を1本** 使います。

```txt
DB の接続数 ≒ pm.max_children × 台数
```

**常駐型（Go）**：プロセスがずっと生きているので、`sql.DB` が接続をプールして使い回します。**接続数はプールの上限で決まります**。

```txt
DB の接続数 ≒ SetMaxOpenConns の値 × 台数
```

- [[1リクエストの流れ]]（⑤）：アプリケーションサーバー → **接続プール** → [[データベースサーバー]]

## 設計で決めること

### 1. プールの上限をいくつにするか
- 選択肢：Go なら `SetMaxOpenConns`（初期値 0 = 無制限）
- 判断の基準：**プールの上限 × 台数 < DB の上限** にする。台数を自動で増やすなら、最大の台数で計算する。例：DB の上限が 300 で、最大 12 台なら、1台あたり 25 未満

```go
db, _ := sql.Open("mysql", dsn)
db.SetMaxOpenConns(20)                  // 同時に使う接続の上限
db.SetMaxIdleConns(20)                  // 空きのまま取っておく数
db.SetConnMaxLifetime(5 * time.Minute)  // 1本の接続を使い続ける最長時間
```

### 2. 空きの接続をいくつ残すか
- 選択肢：Go なら `SetMaxIdleConns`（初期値 2）
- 判断の基準：`SetMaxOpenConns` と同じくらいにすることが多い。初期値の 2 のままだと、20 本使っていても空いたら 2 本しか残さず、次のアクセスの集中で接続を張り直すことになる

### 3. 1本の接続をどれだけ使い続けるか
- 選択肢：Go なら `SetConnMaxLifetime`
- 判断の基準：設定する。DB が別のサーバーに切り替わると、プールに残った古い接続は使えなくなる。一定の時間で作り直すようにしておけば、自然に新しい接続に入れ替わる

## 障害

エラーの文字列で、原因がほぼ分かれます。

| 症状 | 原因 | 確かめ方 |
|---|---|---|
| `Too many connections` | プールの上限 × 台数（作り直す型なら worker 数 × 台数）が DB の上限を超えた | 接続数を計算し直す。「DB が重い」ではなく、アプリの設定の問題であることが多い |
| `connection refused` | DB が止まっている、またはファイアウォールで塞がれている | DB の状態と、通信の許可の設定を見る。アプリのバグではない |
| 接続のタイムアウト | 経路（ネットワークの区画やルート）、または DB の高負荷 | 経路を確かめてから、DB の負荷を見る |
| `invalid connection`、`broken pipe` | 切り替えなどで切れた古い接続を使った | 接続の寿命の設定を見る |
| 使える接続が少しずつ減っていく | 接続を返していない | Go なら `rows.Close()` の書き忘れを探す |

```go
rows, err := db.Query("SELECT ...")
if err != nil { return err }
defer rows.Close()   // これを忘れると接続が返らない
```

## 実行モデルで変わること
→ [[実行モデル]]

| | 作り直す型（PHP-FPM） | 常駐型（Go など） |
|---|---|---|
| 接続の持ち方 | リクエストごとに張って捨てる | プールで使い回す |
| 接続数を決めるもの | worker 数 × 台数 | プールの上限 × 台数 |
| 初期値の危うさ | worker 数で上限がかかる | 上限なし（Go は初期値が無制限） |

## 実装の例

| 環境 | 実装 |
|---|---|
| アプリの中 | Go の `database/sql`、Java の HikariCP など |
| アプリと DB の間 | ProxySQL（オンプレ）、RDS Proxy（AWS）。多数のアプリの接続を、少数の DB の接続に束ねる |
