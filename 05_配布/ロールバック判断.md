# ロールバック判断

デプロイの直後に障害が出たとき、前の版のイメージに戻す（ロールバック）か、修正した版を出す（前方修正）かを決めること。

## なぜ必要か

デプロイ直後の障害は、焦って動くと事態を悪化させやすい場面です。

- 原因探しに時間をかけている間、利用者の被害が広がる
- 慌てて戻した結果、データの不整合という別の障害を起こす

技術よりも **判断の順番** が問われるので、前もって考え方を決めておきます。

大原則は、**まず利用者への影響を止める** ことです。利用者に被害が出ているなら、原因が分からなくても、安全に戻せるなら先に戻します。原因を調べるのは、サービスが落ち着いてからです。「サービスを戻すこと」と「原因を見つけること」は別の仕事なので、同時にやろうとしません。

## 前後のつながり

- [[デプロイの流れ]]（⑧）：[[ローリング更新]] で新しい版に入れ替わる → 障害が出る → **この判断** → 戻すなら、もう一度 [[ローリング更新]]

## 判断の基準

| 基準 | 戻す方に傾く | 様子見・前方修正に傾く |
|---|---|---|
| 影響範囲 | 全員が決済できない、ログインできない | 一部の画面の軽い表示崩れ |
| 戻すコスト | コードだけの変更 | 不可逆なマイグレーション（列の削除など）を含む |
| 原因の見込み | 不明、調査が長引きそう | 数分で直せる、はっきりしたバグ |

## 手順

1. **デプロイが原因かを確かめる**：問題が出始めた時刻が、デプロイした時刻と一致するか。デプロイと関係ない障害（外部サービスの障害など）なら、戻しても直らない
2. **何を変えたかを見る**：コード、設定、マイグレーションのどれを含むデプロイか
3. **マイグレーションを含むなら、戻せるか（可逆か）を確かめる**：列の削除や NOT NULL の追加をした場合、コードだけ戻すと新しいテーブル構造と噛み合わず、二次被害が起きる。消した列のデータは戻らない
4. **上の判断の基準で決める**：戻せる、かつ被害が大きいなら、迷わず戻す。戻せないなら前方修正
5. **戻したら、落ち着いてから原因を調べる**

```txt
被害が出ている
   ↓
安全に戻せる？ ──はい──▶ 戻す → 落ち着いてから原因を調べる
   │
  いいえ（不可逆な変更を含む）
   ↓
前方修正で直す
```

## 事前の備え

### 1. マイグレーションを後方互換で出す
- 何をしておくか：列の削除や名前の変更は、段階に分けて出す → [[DBマイグレーション]]
- 何が楽になるか：問題が出たときに「コードだけ戻す」という選択肢が残る

### 2. イメージに一意のタグを付ける
- 何をしておくか：イメージのタグを git の SHA にする → [[CI]]
- 何が楽になるか：戻すのは「動かすイメージを、前の SHA に変える」だけになる。どれが1つ前の版かも迷わない

### 3. 前の版のイメージを残しておく
- 何をしておくか：コンテナレジストリで、古いイメージを消す決まりを、戻す可能性のある数世代分は残すようにする → [[コンテナレジストリ]]
- 何が楽になるか：戻したいときに、戻す先が無いということがなくなる

### 4. 戻す手順を試しておく
- 何をしておくか：検証の環境などで、実際に前の版に戻してみる
- 何が楽になるか：本番の障害の最中に、初めて手順を調べることがなくなる

## 関連する解説

- [[DBマイグレーション]]：戻せるかどうかを左右する
- [[コンテナレジストリ]]：戻す先のイメージの置き場所
- [[ローリング更新]]：戻すときも同じ流れで入れ替わる
