# DB マイグレーション

テーブル構造の変更をファイルとしてリポジトリに置き、まだ適用していない変更だけを、どの環境の DB にも同じ順番で適用する仕組み。

## なぜ必要か

テーブルに列を足すとき、本番の DB に直接 `ALTER TABLE` を流すと、次の問題が出ます。

- 開発・検証・本番で、テーブル構造がずれていく
- どの変更が、どの環境に適用済みか分からない
- 誰がいつ何を変えたかの記録が残らない

マイグレーションは、変更を **ファイルとしてリポジトリに入れ、適用済みかどうかを DB の中の表で管理** します。どの環境でも、まだ適用していないものだけを順番に流せます。

## 仕組み

```txt
database/migrations/
  ├ 2026_01_10_create_books_table.php       ← 適用済み
  ├ 2026_02_03_add_isbn_to_books_table.php  ← 適用済み
  └ 2026_03_01_add_index_to_books_table.php ← 未適用 → これだけ流す

migrations テーブル（DB の中）に、適用済みのファイル名が記録されている
```

Laravel では `php artisan migrate` で未適用のものを流します。本番では確認を飛ばすために `--force` を付けます。Go では golang-migrate などのツールを使います。

### 新旧のコードが同時に動く

[[ローリング更新]] の間は、**古い版のコードと新しい版のコードが、同じ DB を同時に使います**。マイグレーションは、古いコードでも動く形にしておく必要があります。

## 前後のつながり

- [[デプロイの流れ]]（③）：[[コンテナレジストリ]] にイメージを置く → **マイグレーションを1回だけ流す** → [[オーケストレーション]] が新しい版に入れ替える

## 設計で決めること

### 1. 変更を1回で出すか、段階に分けるか
- 選択肢：1回で出す／先に広げて、あとで縮める（expand / contract）
- 判断の基準：古いコードが動かなくなる変更は、段階に分ける

| 変更 | 1回で出してよいか |
|---|---|
| 列の追加（NULL 可、または初期値あり） | よい |
| テーブルの追加 | よい |
| 列の削除・名前の変更 | だめ。段階を分ける |
| NOT NULL の追加 | だめ。古いコードが値を入れずに書き込んで失敗する |

列の名前を `title` から `name` に変える場合：

```txt
リリース1：name 列を追加する。コードは両方に書き込む
リリース2：コードを name だけ読むように変える
リリース3：title 列を消す
```

### 2. いつ、どこで流すか
- 選択肢：コンテナの起動時に流す／デプロイの手順の中で1回だけ流す
- 判断の基準：デプロイの手順の中で1回だけ流す。起動時に流すと、複数のコンテナが同時に起動したとき、**同じマイグレーションが同時に何本も走って競合** する

### 3. 大きなテーブルを変えるとき、止まる時間をどう扱うか
- 選択肢：そのまま流す／止まる時間を確かめてから流す／止めずに変える方法（オンラインでのスキーマ変更）を使う
- 判断の基準：行数の多いテーブルに列やインデックスを足すと、処理に時間がかかり、その間書き込みが止まることがある。本番と同じくらいのデータ量で、かかる時間を事前に確かめる

## 障害

| 症状 | 原因 | 確かめ方 |
|---|---|---|
| デプロイ中に古い版でエラーが出る | 後方互換でない変更（列の削除など）を出した | そのデプロイのマイグレーションに、列の削除・名前の変更・NOT NULL の追加がないか見る |
| マイグレーションが二重に流れて失敗する | 起動時に流していて、複数のコンテナで競合した | マイグレーションを流している場所を見る |
| マイグレーション中にサービスが止まる | 大きなテーブルの変更で、書き込みが止まった | DB で実行中の処理とロックの待ちを見る |
| コードを戻したのに直らない | テーブルの構造は新しいまま。古いコードと噛み合わない | → [[ロールバック判断]] |

コードは前の版に戻せても、**消した列のデータは戻りません**。後方互換を守っておくと、問題が起きたときに「コードだけ戻す」という安全な選択肢が残ります。
