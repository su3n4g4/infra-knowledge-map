# CI（継続的インテグレーション）

リポジトリに push されるたびに、決まった環境でテストを実行し、本番に出せる形（コンテナイメージなど）まで自動で作る仕組み。

## なぜ必要か

人の手でビルドしてデプロイしていると、次のようなことが起きます。

- テストを走らせ忘れたまま本番に出す
- 自分の PC の環境でビルドしたため、他の人の環境と結果が違う
- 誰が、どのコードを、いつ本番に出したか分からない

CI は、**決まった環境で、決まった手順を、毎回必ず実行する** ことで、これを防ぎます。壊れたコードはテストの段階で止まり、本番まで届きません。

## 仕組み

```txt
git push
   ↓ 自動で起動
CI のサーバー
   ├ ① ソースを取得
   ├ ② 依存ライブラリを入れる
   ├ ③ テストを走らせる       ← 失敗したらここで止まる
   ├ ④ docker build でイメージを作る
   └ ⑤ コンテナレジストリにイメージを置く  ← タグは git の SHA
```

手順はリポジトリの中にファイルで書きます。GitHub Actions なら `.github/workflows/` に置きます。

```yaml
on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: make test                         # テスト
      - run: docker build -t app:${{ github.sha }} .
      # 以降、コンテナレジストリへログインして push する
```

### CI と CD
- **CI**（継続的インテグレーション）：テストとビルドまで
- **CD**（継続的デリバリー／デプロイ）：作ったものを本番に出すところまで

実際には両方をひと続きの流れで組むことが多く、まとめて CI/CD と呼ばれます。

## 設計で決めること

### 1. イメージのタグをどう付けるか
- 選択肢：git の SHA／バージョン番号／`latest` のような使い回す名前
- 判断の基準：git の SHA かバージョン番号にする。`latest` だと、いま本番で動いているのがどのコードか分からなくなり、戻すときにも指定できない → [[ロールバック判断]]

### 2. 秘密情報をどう渡すか
- 選択肢：イメージに入れる／実行するときに環境変数や秘密情報の保管サービスから渡す
- 判断の基準：実行するときに渡す。イメージに入れると、イメージを取得できる人なら誰でも読める

### 3. CI に外の環境を操作させる権限をどう持たせるか
- 選択肢：長期間有効な鍵を CI に保存する／実行のたびに一時的な権限を受け取る
- 判断の基準：一時的な権限にする。鍵が漏れたときの被害が小さい。GitHub Actions から AWS を操作するなら、OIDC という仕組みで一時的な権限を受け取る

### 4. 失敗したときにどうするか
- 選択肢：止める／警告だけ出して進める
- 判断の基準：止める。失敗を無視して通す設定にすると、CI がある意味がなくなる

## 障害

| 症状 | 原因 | 確かめ方 |
|---|---|---|
| 手元では通るのに CI で失敗する | 手元にだけある設定やファイルに依存している | CI のログで、どの手順で何が足りないかを見る |
| CI がとても遅い | 依存ライブラリやイメージの層を、毎回ゼロから作っている | キャッシュを使っているか見る |
| 本番で動いているコードが分からない | タグを使い回している | 本番のイメージのタグとダイジェストを見る |
