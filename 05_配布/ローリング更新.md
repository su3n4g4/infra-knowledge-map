# ローリング更新

新しい版のコンテナ（またはサーバー）を少しずつ起動し、ヘルスチェックに通ったものから順に、古い版を止めて入れ替えるデプロイの方法。

## なぜ必要か

全部のサーバーを一度に止めて、新しい版で起動し直すと、その間サービスが止まります。また、新しい版に問題があると、全部が一斉に壊れます。

ローリング更新は、**少しずつ入れ替え、新しい版が正常に動くことを確かめてから次へ進む** ので、サービスを止めずに済み、問題があれば途中で止められます。

## 仕組み

```txt
はじめ：v1 v1 v1 v1
  ↓ v2 を1個起動し、ヘルスチェックに通るのを待つ
        v1 v1 v1 v1 v2
  ↓ v1 を1個、ロードバランサーから外して止める
        v1 v1 v1 v2
  ↓ これを繰り返す
おわり：v2 v2 v2 v2
```

1回分の入れ替えでは、次のことが起きています。

1. 新しい版（v2）を起動する
2. [[ヘルスチェック]] に通るのを待つ
3. 古い版（v1）を [[ロードバランサー]] の転送先から外す
4. v1 に終了のシグナルを送り、処理中のものを終えてから止める → [[グレースフルシャットダウン]]

## 前後のつながり

- [[デプロイの流れ]]（⑤）：[[オーケストレーション]] が動かすイメージを v1 → v2 に変える → **ローリング更新** → 全部が v2 に

## 設計で決めること

### 1. 一度に何個入れ替えるか
- 選択肢：一時的に数を増やして入れ替える（先に v2 を起動してから v1 を止める）／数を増やさずに入れ替える（先に v1 を止めてから v2 を起動する）
- 判断の基準：余分に起動する CPU・メモリがあるなら、増やして入れ替える。処理できる量が途中で減らない。余裕が無ければ、一時的に処理できる量が減ることを受け入れて、増やさずに入れ替える

### 2. 新旧が同時に動いても困らないようにするか
- 選択肢：両方の版で使える形にしておく／一度に切り替える方式（Blue/Green）にする
- 判断の基準：ローリング更新では、入れ替えの間 **v1 と v2 が同時にリクエストを処理** する。DB のテーブル構造（→ [[DBマイグレーション]]）、セッションやキャッシュのデータの形、外部に公開している API の形を、両方の版で使える形にしておく

### 3. 失敗したら自動で止めるか
- 選択肢：自動で止めて前の版に戻す／人が判断する
- 判断の基準：自動で止める仕組みがあるなら使う。新しい版が何度起動しても正常にならないとき、壊れた版が本番に居座るのを防げる

### 4. ローリング更新か Blue/Green か

| | ローリング更新 | Blue/Green |
|---|---|---|
| 進め方 | 少しずつ入れ替える | 新しい環境を丸ごと用意し、一度に切り替える |
| 新旧の同時稼働 | ある | 切り替えの瞬間だけ |
| 戻すとき | もう一度入れ替える | 前の環境に切り替え直すだけ（速い） |
| 費用 | 少し余分に起動するだけ | 一時的に倍の環境が要る |

- 判断の基準：多くの場合はローリング更新で足りる。戻す速さを最優先するなら Blue/Green

## 障害

| 症状 | 原因 | 確かめ方 |
|---|---|---|
| デプロイがいつまでも終わらない | 新しい版がヘルスチェックに通らない | 新しい版の起動時のログと、ヘルスチェックの結果を見る |
| デプロイのたびに少し 502 が出る | 古い版を止めるとき、処理中のリクエストを切っている | → [[グレースフルシャットダウン]] |
| デプロイ中だけエラーが出る | 新旧の版で、DB やデータの形が噛み合っていない | 新旧が同時に動いていることを前提に、その間の変更を見直す |
| 入れ替え中に新しい版が起動できない | 一時的に増えるぶんの CPU やメモリが足りない | 一度に入れ替える数と、空いている資源を見る |
| 1回のデプロイに数十分かかる | ヘルスチェックの間隔や、外すときの待ち時間が長い | それぞれの設定値を見直す |

## 実装の例

| 環境 | 実装 |
|---|---|
| オンプレ | ロードバランサーから1台ずつ外して更新するスクリプト、Ansible など |
| Kubernetes | Deployment の RollingUpdate |
| AWS | [[ECS]] のサービスのデプロイ（最小ヘルス率・最大率で、一度に入れ替える数を決める） |
