# コンテナレジストリ

ビルドしたコンテナイメージを保存しておくサーバー。CI がイメージを置き（push）、アプリを動かすサーバーがそこから取得（pull）して起動する。オンプレでは Harbor など、AWS では ECR で実現する。

## なぜ必要か

コンテナを使う目的の1つは、**全部のサーバーで、まったく同じものを動かす** ことです。そのためには、ビルドしたイメージを1か所に置き、全部のサーバーがそこから取ってくる必要があります。サーバーごとにビルドすると、ビルドした時点の違いで中身がずれることがあります。

もう1つの目的は、**前の版にすぐ戻せる** ことです。過去のイメージを残しておけば、問題が起きたときに「前の版のイメージを動かす」だけで戻せます → [[ロールバック判断]]

## 仕組み

```txt
CI ──push──▶ コンテナレジストリ
              └ リポジトリ「my-app」
                  ├ my-app:3f9a2c1  ← 今の本番
                  ├ my-app:a81b7d0  ← 1つ前
                  └ my-app:5c2e9f4  ← 2つ前

サーバー ──pull──▶ 「my-app:3f9a2c1」を取ってきて起動
```

| 言葉 | 意味 |
|---|---|
| リポジトリ | イメージを入れる箱。アプリごとに1つ作ることが多い |
| タグ | イメージに付ける名前。`3f9a2c1` のように git のコミットの SHA を使うことが多い |
| ダイジェスト | イメージの中身から計算した値（`sha256:...`）。中身が1バイトでも違えば変わる |
| push / pull | 置く / 取ってくる |

タグは人が付ける名前なので、同じタグに別の中身を上書きできてしまうことがあります。ダイジェストは中身そのものから決まるので、上書きできません。

## 設計で決めること

### 1. タグをどう付けるか
- 選択肢：git のコミットの SHA／バージョン番号（`v1.2.3`）／`latest` のような使い回す名前
- 判断の基準：git の SHA かバージョン番号にする。`latest` だと、いま本番で動いているのがどのコードか分からなくなり、戻すときにも指定できない

### 2. 同じタグへの上書きを許すか
- 選択肢：許す／禁止する
- 判断の基準：禁止する。上書きできると「同じタグなのに中身が違う」状態が起き、戻したつもりで戻っていないことがある

### 3. 何世代残すか
- 選択肢：すべて残す／決まった数や日数で古いものを消す
- 判断の基準：保存の費用と、戻したい範囲で決める。消すなら、少なくとも戻す可能性のある数世代は残す

### 4. 誰が push・pull できるか
- 選択肢：push は CI だけ、pull は本番のサーバーだけ、のように分ける／誰でもできる
- 判断の基準：分ける。誰でも push できると、テストを通っていないイメージが本番に入りうる

### 5. 中身の脆弱性を確かめるか
- 選択肢：push のたびに確かめる（スキャン）／確かめない
- 判断の基準：確かめる。イメージに入っている OS やライブラリに、既知の脆弱性が含まれていないかが分かる

## 障害

| 症状 | 原因 | 確かめ方 |
|---|---|---|
| サーバーがイメージを取得できず、起動しない | 取得する権限が無い、タグの指定が間違っている、サーバーからレジストリまでの経路が無い | 起動のログに出る取得のエラーを見る。プライベートなネットワークに置いたサーバーなら、外へ出る経路を確かめる |
| 戻そうとしたら、前のイメージが無い | 古いイメージを消していた | 消す設定（何世代残すか）を見る |
| 同じタグなのに、サーバーごとに動きが違う | タグを上書きした | 各サーバーで動いているイメージのダイジェストを比べる |
